The multiverse

View as MarkdownOpen in ClaudeOpen in ChatGPT

The multiverse replays a captured match up to turn N, forks it, and plays K variants from there: other grafts, other tunables, other presets, other bots. Because the rules are deterministic, any difference is caused by the variant. Scion reports, per variant, whether the rules diverged, the first turn and the first field that changed, and shows the visuals side by side in a mosaic. It is how you prove a graft is only visual, and how you see what a balance change does to a real match.

When to use

Section titled “When to use”
  • Before promoting a graft: run the match with and without it; nothing may diverge.
  • When tuning rules: see the first turn where a new damage value changes the outcome.
  • When a bug appears late in a match: fork just before it and try fixes.

Before you begin

Section titled “Before you begin”
  • Adoption level 3: the rules registered as an ISimulation, deterministic in plain .NET (Find non-determinism).
  • A captured match (Turn any match into a recipe).
  • For grafts: variants and presentation tunables: a test build (dotnet scion build test), and an IMatchCapture whose Replay writes a turn event with the state hash after every turn.

Steps

Section titled “Steps”

1. Fork and run

Section titled “1. Fork and run”

crit-1200 is a preset that sets the rule tunable Balance.CritPermille to 1200, so it runs on the core simulator. heavy is a feel preset of graft tunables (CritShake.Strength and others), so it runs in the test build.

2. Read the report

Section titled “2. Read the report”

multiverse.json has the hash of every turn for the base and each variant, and for diverged variants the field’s value before and after.

3. See it

Section titled “3. See it”

With --mosaic, the test build replays the variants side by side from the fork turn and writes mosaic.png.

Reference

Section titled “Reference”

Variants

Section titled “Variants”
Kind Given as Changes Runs on
preset a preset name or blend tunables the core simulator when every tunable is in the core assembly; otherwise the test build
tunables tunable:Balance.CritPermille=1200 one or more tunables the same rule as preset
grafts grafts:<dll> presentation code (the rules must not diverge) the test build, always
bot bot:<name> who plays the remaining turns the core simulator

--variants takes a comma-separated list, or a JSON file with one object per variant.

How it runs

Section titled “How it runs”

Each variant runs where the code it changes runs: rule variants on the core simulator, presentation variants in the test build.

On the core simulator

Section titled “On the core simulator”

Rule variants (rule tunables, presets of rule tunables, bots) change only what the ISimulation reads:

  1. The ISimulation replays the match’s commands up to --at-turn and saves the state (ISaveable).
  2. For each variant, it loads the state, applies the variant and plays the remaining commands (or the bot).
  3. After every turn it records Hash(); the first turn whose hash differs from the base is first_turn.
  4. At that turn, IInspectable.Diff names the first field that differs (units[0].hp).

These steps run in plain .NET, in parallel, in milliseconds per turn.

In the test build

Section titled “In the test build”

A graft hangs on a game method such as HitPresenter.Play, which the plain .NET ISimulation never calls; the same holds for tunables read by presentation code. On the core simulator such a variant could never diverge, so it would prove nothing. These variants run in the test build instead:

  1. One copy replays the match without changes (-scion-match <file>): the base. After every turn, Replay writes a turn event with the state hash.
  2. Each variant gets its own copy. It replays the same commands to --at-turn, then applies the variant at that turn boundary (the DLL is injected through the copy’s control channel; tunables are set) and plays the remaining turns, writing the same turn events.
  3. The CLI compares the per-turn hashes of each variant with the base, turn by turn; the first that differs is first_turn.
  4. At that turn, both copies save the state (ISaveable) and IInspectable.Diff names the first field that differs.

A grafts: variant whose hashes match the base on every turn after the fork really leaves the rules alone, because the graft ran on every presentation call of the replay. This takes seconds per variant (one copy each), and the copies run in parallel. --mosaic uses the same copies to write mosaic.png.

Errors

Section titled “Errors”
Code Exit Cause Next action
no_simulation 3 No [assembly: Simulation]. Register an ISimulation.
not_forkable 3 The simulation does not implement ISaveable. Implement Save and Load on the state.
no_match 2 The match file or a variant does not exist. trial list shows captured matches.
variant diverged with grafts 1 A graft changed rules. Move the change to the core (Grafts are visual only).

Prove a draft graft is visual

Section titled “Prove a draft graft is visual”

Take the DLL path from the dll field of graft build. Both variants replay in the test build, and the graft runs on every hit of the match. Exit 0 with diverged: false means the state hash matched the base after every turn. For a recipe instead of a match, trial run <Id> --grafts <dll> gives the same proof on one recipe: hash: same against the baseline.
