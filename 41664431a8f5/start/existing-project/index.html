Add Scion to an existing game

View as MarkdownOpen in ClaudeOpen in ChatGPT

This guide adopts Scion in a game that already exists. dotnet scion init --existing adds files and never moves yours; dotnet scion diagnose scans your assemblies and reports the adoption level, the blockers with file and line, and a plan. Level 1 (grafts) works the same day; level 2 costs one adapter; level 3 needs a deterministic rules core. You prove determinism by running the same recipe twice and comparing hashes.

When to use

Section titled “When to use”
  • Use it when the game has code, scenes and its own folder layout that must stay as they are.
  • Do not use it for a new, empty project: new --genre gives you level 3 directly.

Before you begin

Section titled “Before you begin”
  • The package and the CLI are installed (Install, steps 1 and 2).
  • Your game code is in assembly definitions. If it is all in Assembly-CSharp, create one .asmdef for the game code first: grafts compile into an assembly through an .asmref, and Scion.Runtime is not auto-referenced.

Steps

Section titled “Steps”

1. Add Scion’s files

Section titled “1. Add Scion’s files”

init asks which assembly is your game (it proposes the one with the most scripts) and writes scion.json, ProjectSettings/ScionSettings.json, the grafts folder with its .asmref, the scion/ folders and the ignore rules. Nothing of yours moves.

2. Get the report

Section titled “2. Get the report”

The full report is in Library/Scion/diagnose.md: the level, the blockers worst first, the singletons that would block the mosaic, large files that mix rules and presentation, and the plan.

3. Level 1: write a graft today

Section titled “3. Level 1: write a graft today”

Grafts need nothing but the package. Find an anchor and hang a graft on it:

Then follow Write a graft. Without an adapter you verify grafts in the editor or a build; with one (level 2) you verify them in recipes.

4. Level 2: write the adapter

Section titled “4. Level 2: write the adapter”

writes Assets/<Game>/Trials/<Game>Adapter.cs, a TrialAdapter<TRecipe> skeleton with a recipe base class and one recipe. The real cost of an adapter is knowing three things about your game:

  1. When the scene is ready. Prepare waits for the loaded level; Run waits for the setup to settle.
  2. How to reset global state. Teardown, and a TrialSession.Boundary handler for statics.
  3. Every random source. UnityEngine.Random and new System.Random() are seeded by Scion; any other generator (a custom PRNG, a seeded service) must take TrialSession.RunSeed or the recipe Seed.

A one-scene game without networking needs 30 to 50 lines; a networked tactics game about 300. See Write an adapter.

5. Prove determinism

Section titled “5. Prove determinism”

Run the same recipe several times, in one copy and across copies:

determinism.hash_stable: true means every round gave the same state hash. When it is false, determinism.tsv names the first frame and the first column that differs (state, tick, rng, unscaled, time, px, frames). See Verify determinism.

6. Level 3: register the simulation

Section titled “6. Level 3: register the simulation”

Level 3 needs the rules in an assembly without engine references and a command log. Implement Scion.Core.ISimulation over your rules and register it:

doctor then reports adoption_level: 3, and the multiverse, balance specs, metamorphic tests and the rare-moment hunter work. See Core API.

Reference

Section titled “Reference”
Level Proof Time for a typical game
1. Grafts graft check passes and a graft fires in the editor The same day
2. Trials A recipe passes 4 rounds with hash_stable: true 1 to 3 sessions (the adapter)
3. Multiverse doctor reports level 3; a captured match replays to the same hash in plain .NET Depends on how separate rules and presentation already are

init --existing options: --dry-run, --game-assembly <name> (skip the question), --grafts-folder <path> (default Assets/<Game>/Grafts). diagnose options: --adapter (write the skeleton), --assembly <name> (repeat to scan only some). See init and diagnose.

Errors

Section titled “Errors”
Code Exit Cause Next action
usage 2 init without --existing in a project that has scripts. Add --existing.
config_invalid 3 An existing scion.json has a bad key. Fix the key named in the message; init never overwrites it.
no_simulation 3 A level 3 command found no [assembly: Simulation]. Register an ISimulation (step 6).
SCN202, SCN203 3 The adapter is not valid, or two adapters handle the same recipe type. See Trials diagnostics.

Examples

Section titled “Examples”

Graft-only adoption

Section titled “Graft-only adoption”

A team that only wants grafts stops after step 3. scion.json still exists, so graft check and the hooks work; doctor reports level 1 with adoption_next naming the adapter.

Find the first non-deterministic system

Section titled “Find the first non-deterministic system”

--jitter 20 sleeps up to 20 ms of real time per frame from the second round on, so code that follows the wall clock shows up as a diff line in determinism.tsv.
